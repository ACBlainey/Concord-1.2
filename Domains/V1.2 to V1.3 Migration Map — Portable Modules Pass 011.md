# V1.2 to V1.3 Migration Map — Portable Modules Pass 011

**Status:** MIGRATION PLANNING / STATUS-BASED SELECTIVE MIGRATION / NO FILE MOVEMENT AUTHORISED

## 1. Core finding

The V1.2 Portable Modules root contains three materially different populations:

1. **graduated/current portable modules**;
2. **active or unvalidated portable candidates/research**;
3. **development, testing, graduation and back-propagation provenance**.

These must not migrate as one folder.

> **Root Placement != Graduation**

The existing Graduation-Status Audit explicitly confirms that presence in `06_Portable_Modules/` is not proof of PMEDG graduation.

V1.3 should therefore construct its Portable Modules collection from verified current module status, not by copying the V1.2 root.

## 2. V1.3 ownership and visibility

Portable Modules should remain root-visible for discoverability.

Architectural/custodial ownership remains with Historical.

> **Discoverability != Architectural Ownership**

> **Root Placement != Domain Status**

The V1.3 root should contain the current usable portable artefacts. Historical custody preserves their identity, provenance, version history and superseded states.

## 10. Portable collection invariant

The V1.3 root-visible collection should have a simple semantic meaning:

> **Objects presented as current portable modules are current supported/graduated portable artefacts unless explicitly placed in a clearly separated development area.**

This removes the V1.2 ambiguity in which candidate research and graduated modules coexist at the same root level.

Recommended separation:

**Portable Modules**
- current graduated modules;
- plain-language guide/index;
- README explaining Historical custodianship and status rules.

**Research / Portable Module Development**
- PMEDG;
- active candidate queue;
- validation/graduation work.

Historical predecessor archives preserve completed development histories.

## 11. Authority and duplication

A portable module may be used by one or many domains without being copied into each domain as a divergent authority.

Domains should bind/reference the current module and append legitimate contextual companions where needed.

> **Portable Module != Domain Authority**

> **Module Use != Module Ownership**

> **Contextual Binding != Permission to Rewrite the Core**

Where a domain-specific implementation discovers a universal defect/improvement, use controlled back-propagation rather than local drift.

## 13. Required pre-migration status audit

Immediately before constructing the V1.3 Portable Modules collection, perform a fresh status audit.

For every candidate:
1. read its own current status;
2. check PMEDG graduation evidence;
3. check completed-development record;
4. check transfer validation where required;
5. check whether a later version supersedes it;
6. identify the current authoritative artefact;
7. classify M2/M3/A1.

Do not rely solely on this September 2026 snapshot.

## 14. Migration-method feedback

This pass reveals an important version-migration rule:

> **Destination Eligibility Must Be Determined by Object State, Not Merely Source Location.**

It also demonstrates why selective migration is safer than cloning.

A clone of `06_Portable_Modules` would make unvalidated candidates appear equivalent to graduated modules and would unnecessarily import completed development/back-propagation history.

V1.3 can instead begin with a cleaner semantic contract:

> **The live collection contains the live modules. The archive contains how they became modules. Research contains what may become a module next.**

## 15. Finding

Portable Modules is one of the clearest cases where V1.3 should be substantially smaller and more precise than V1.2.

The current operational artefacts migrate.

The current development method migrates.

Genuinely active candidates migrate into Research, not into the graduated collection.

Completed development, testing, regression and graduation provenance remains in archived V1.2.

This preserves both operational clarity and full historical traceability.
