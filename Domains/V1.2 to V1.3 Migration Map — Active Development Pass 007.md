# V1.2 to V1.3 Migration Map — Active Development Pass 007

**Status:** MIGRATION PLANNING / SOURCE-RESOLVED / NO FILE MOVEMENT AUTHORISED

## 1. Core finding

08_Active_Development is not a civilisational domain.

It is a **development-state pipeline** containing work from many different civil functions.

Its current top-level categories — Sketch Ideas, Development Notes, Candidate Principles, Candidate Architecture and Experiments — describe **maturity/state of work**, not what the civilisation does.

V1.3 should therefore not preserve Active Development as a peer root beside civil architecture.

> **Development State != Civil Function**
>
> **Where Work Is Developed != What the Developed System Is**

The active development function belongs inside the **Research domain**, while outputs graduate to their legitimate functional owners and completed development history passes to Historical.

## 2. V1.3 development lifecycle

A general route is:

**QUESTION / OBSERVATION / EDGE CASE**
-> **SKETCH / HYPOTHESIS**
-> **DEVELOPMENT NOTE**
-> **CANDIDATE PRINCIPLE / ARCHITECTURE**
-> **TEST / ADVERSARIAL EXAMINATION**
-> **VALIDATION / GRADUATION REVIEW**
-> **GRADUATED OUTPUT TO LEGITIMATE OWNER**
-> **DEVELOPMENT PROVENANCE TO HISTORICAL**

This preserves the useful V1.2 workflow without allowing development state to define the permanent repository topology.

## 9. Graduation rule

The key V1.3 rule should be:

> **Research Owns Development Until the Output Has a Legitimate Functional Owner.**

After graduation:

> **The Owner Receives the Current Architecture; Historical Receives the Developmental Provenance.**

Research may continue evaluating the graduated system without retaining ownership of it.

This creates:

**RESEARCH DEVELOPS**
-> **OWNER DOMAIN OPERATES**
-> **RESEARCH TESTS**
-> **HISTORICAL PRESERVES**

## 10. Relationship to PMEDG

Domain/system development and portable-module development must remain distinct.

PMEDG asks whether a reusable module can be extracted, tested and graduated.

The broader Civilisational Development pipeline asks how any candidate civil architecture moves from observation to legitimate integration.

A development output may therefore:
- become a domain architecture;
- become cross-domain architecture;
- become a portable module;
- become a constitutional constraint;
- remain research;
- be rejected;
- or reveal a new question.

## 12. Naming and expectation audit requirement

The migration work has now shown that inherited labels can create false expectations about ownership and function.

Before V1.3 domain names are finalised, perform a **Domain Naming and Expectation Audit** for all provisionally frozen domains.

For each domain test:

1. What persistent civil function was actually discovered?
2. What does the current/conventional name imply?
3. Which legitimate functions does the name hide?
4. Which functions does it falsely imply ownership of?
5. Does Concord materially redefine the conventional concept?
6. Would a different name better preserve the discovered architecture?
7. Would the new name itself create misleading expectations?

Governing rule:

> **Define the Function First. Derive the Boundary Second. Name the Domain Last.**

Names are architecturally consequential because:

> **Name -> Expectation -> Assumed Function -> Architectural Constraint**

The audit should not automatically reopen the 18-domain topology. A functional domain may be correctly identified while its inherited label is wrong.

## 13. Finding

V1.3 should have no root-level Active Development area.

The valuable process survives inside Research.

This removes another major piece of project-shaped repository architecture and replaces it with living-civilisation architecture without erasing how the civilisation was developed.
