# V1.2 to V1.3 Migration Map — Applications Pass 012

**Status:** MIGRATION PLANNING / SELECTIVE APPLICATION MIGRATION / NO FILE MOVEMENT AUTHORISED

## 1. Core finding

`07_Applications` is already conceptually well separated from constitutional and domain authority.

Its README states:

**APPLICATION AND DEVELOPMENT AREA / NOT CANONICAL CONSTITUTIONAL AUTHORITY**

and:

**VALIDATION VARIES BY APPLICATION; COMPREHENSIVE VALIDATION NOT ESTABLISHED**

This boundary should be preserved in V1.3.

> **Principle != Mechanism != Architecture != Implementation != Outcome**

Applications are not domains merely because they instantiate several domains.

Applications are places where current Concord architecture is assembled in a bounded context and can generate practical evidence.

## 2. V1.3 root treatment

Retain a root-level **Applications and Implementations** area.

Its purpose is to hold:
- current applied Concord architectures;
- implementation specifications;
- bounded pilots;
- deployment-specific adaptations;
- live design studies where the application itself is intentionally maintained.

It should not become a substitute for Research, Domains or Cross-Domain Architecture.

Accordingly it should be treated as **legacy-established/current unless later source resolution demonstrates otherwise**.

> **Foundational Application Specification != Constitutional Principle**

> **Cross-Domain Use != Cross-Domain Authority**

## 6. Mars First

`Mars first.md`

The document explicitly describes itself as an integrated design study and says Mars First evolved from a case study into a way to combine multiple strands of Concord research.

It asks how a new civilisation might be designed under Martian constraints.

### Treatment
**M1/M3 — MIGRATE AS CURRENT APPLICATION/DESIGN STUDY** if Mars First remains an active Concord application in V1.3.

It must retain its epistemic boundary:
- it is not proof of a complete Concord civilisation;
- it is not authority for Earth implementation;
- it may expose assumptions and generate evidence;
- some incorporated systems may themselves have different maturity states.

Mars First should reference current versions of the systems it uses rather than freezing old copies where avoidable.

## 7. Applications as evidence generators

Preserve the current application feedback model:

**Architecture**
→ Application
→ Pilot
→ Observation
→ Evidence
→ Evaluation
→ Correction

A failed application does not automatically invalidate the underlying principle.

A successful application does not automatically prove universal validity.

Application findings should route into Research and, where justified, controlled architectural revision.

> **Application Result != Universal Proof**

> **Failure to Fit the Model May Be Information About the Model**

## 8. Application/domain relationship

Applications may combine:
- Governance;
- Economy/Value;
- Infrastructure;
- Planning;
- Environment;
- Research;
- Continuity;
- Civil Attention;
- Education;
- Health;
- and other domains.

This does not make the application a super-domain.

The application owns the bounded implementation context.

Each participating domain retains authority over its own civil function.

> **Integrated Application != Integrated Authority**

## 9. Legacy-state issue

Applications are especially likely to expose the legacy-status problem identified during migration.

A working application may depend on a method whose original document remains labelled:
- candidate;
- development;
- experimental;
- or ungraduated,

because the application incorporated it before later graduation methodology existed.

Therefore application dependency graphs are useful evidence for the planned V1.3 Legacy Architecture State and Graduation Reconciliation Audit.

Where an application clearly depends upon a supposedly undeveloped object, that dependency should trigger source resolution rather than automatic demotion of the object.

> **Operational Dependency Is Evidence of Architectural State, Not Automatic Proof of Validation.**

## 11. V1.3 structural implication

The Applications root should contain **applications**, not all research and development generated by them.

Where Mars First or GTP generates:
- a new general principle;
- a portable module;
- a domain architecture;
- a research programme;
- a cross-domain mechanism;

that result should graduate or move to its legitimate owner.

The application may retain a reference to the resulting architecture.

This avoids Applications becoming another catch-all development root.

## 12. Finding

The V1.2 Applications area requires relatively little conceptual correction.

Its strongest existing rule should survive:

> **A Failed Application Does Not Automatically Invalidate the Principle.**

and its inverse:

> **A Successful Application Does Not Automatically Prove Universal Validity.**

For V1.3, the main improvement is structural: retain current applications as bounded implementations, route generalised results outward to their legitimate owners, and leave completed application-development provenance in the predecessor archive.

GTP provides a useful example of **legacy-established current architecture** whose maturity should be judged from its actual specification, incorporation and use rather than solely by whether it passed a methodology formalised later.
