# V1.2 to V1.3 Migration Map — Open Questions Pass 013

**Status:** MIGRATION PLANNING / QUESTION-STATE CONSOLIDATION / NO FILE MOVEMENT AUTHORISED

## 1. Core finding

`09_Open_Questions` already contains an important distinction that should become stronger in V1.3:

> **Historical Audit Record != Current Open-Question State**

The current V1.2 structure is transitional. It contains:
- a primary current Open Questions register;
- two recovery registers;
- a Closed Questions area;
- a housekeeping instruction to consolidate the registers.

The recovery structure was created to avoid information loss while reconstructing live questions from earlier material.

V1.3 should migrate the **current unresolved research objects**, not preserve the temporary recovery topology.

## 2. Architectural status of Open Questions

Open Questions is not itself a civilisational domain.

An open question is a **knowledge/development state** attached to some part of the architecture.

Questions may concern:
- constitutional architecture;
- a domain;
- cross-domain architecture;
- portable modules;
- applications;
- Research methodology;
- system gaps;
- empirical validation;
- or the Concord as a whole.

For discoverability, V1.3 may retain a root-level Open Questions index/register.

> **Root Visibility != Domain Status**

Research is the natural operational owner of active uncertainty, while the relevant domain/system remains the subject of the question.

Historical preserves prior question states and closure history.

## 3. Primary current register

`Current Open Questions — Concord V1.2.md`

Status:

**CURRENT OPEN-QUESTION REGISTER / ACTIVE RESEARCH MAP / NOT CANONICAL ARCHITECTURE**

### Treatment
**M1/M3 — MIGRATE CURRENT QUESTION STATE**, but regenerate as a V1.3 register rather than copying unchanged.

Questions must be rechecked against the migrated architecture.

A V1.2 question may by migration time be:
- still open;
- partly resolved;
- architecturally addressed but validation-open;
- superseded;
- decomposed;
- moved to a domain-specific research programme;
- or stale because later V1.2 work answered it.

Therefore migration should preserve the question object while allowing its current state to be reconciled.

### Treatment
**M4 — EXTRACT LIVE QUESTIONS INTO V1.3 CURRENT REGISTER**

The recovery file itself is V1.2 consolidation provenance and remains in the predecessor archive.

## 5. Recovery Register 03 — Multisubstrate Justice

Same structural issue.

It preserves narrower explicit live questions that would otherwise disappear inside broader categories.

### Treatment
**M4 — EXTRACT LIVE QUESTIONS INTO V1.3 CURRENT REGISTER**

Preserve the important rule:

> **A Broad Surviving Domain Does Not Count as Full Survival If an Independently Testable Sub-Question Has Disappeared Inside It.**

The recovery wrapper itself remains V1.2 provenance.

## 6. Closed Questions

The Closed Questions area contains questions that were:
- answered at a defined conceptual level;
- retired;
- rejected as premises;
- moved outside Concord scope;
- or architecturally addressed.

### Default treatment
**A1 — ARCHIVE IN PREDECESSOR**

V1.3 does not need to carry a complete duplicate ledger of every question that V1.2 closed.

The intact predecessor already preserves that historical state.

### Exceptions
Use **M4/A2** where a current V1.3 system needs:
- a reopening condition;
- a current bounded conclusion;
- a warning against a known false premise;
- an unresolved empirical validation requirement;
- or a live dependency on the closure rationale.

The current conclusion should normally migrate to its legitimate architectural owner, not remain solely in a Closed Questions register.

> **Closed Question History != Current Architecture**

> **Current Conclusion Should Live With the System It Now Informs**

## 7. ARCHITECTURALLY ADDRESSED / VALIDATION OPEN

This status is particularly important.

A conceptual architecture can answer:
**How might this problem be addressed?**

without answering:
**Does this architecture actually work?**

Therefore:

> **Architecture Is Not Proof**

Questions with this state should normally remain live in V1.3 Research even where the associated architecture migrates as current/corrigible.

This avoids conceptual graduation silently becoming empirical validation.

## 8. Permanent adversarial questions

Some questions are intentionally designed not to close permanently.

Examples may ask whether:
- the Concord actually works;
- long-term stability persists;
- institutional capture is occurring;
- the ethical kernel remains sufficient;
- a supposedly safe architecture has developed hidden failure modes.

### Treatment
**M1/M3 — MIGRATE AS PERMANENT OR RECURRING RESEARCH OBJECTS**

These are not unfinished architecture in the ordinary sense. They are persistent correction mechanisms.

> **A Question Can Be Permanently Valuable Without Being Permanently Unanswered in the Same Way.**

Its evidence/state may change while the adversarial question remains available.

## 9. Relationship to domains

V1.3 should support both:
- a central discoverability index;
- local ownership/context.

Recommended pattern:

**Root Open Questions Index**
→ Question ID
→ current status
→ subject/owner
→ research programme
→ dependencies
→ current evidence
→ next test
→ local domain/system question record where needed.

This preserves one discoverable civilisational uncertainty map without creating a central authority over all research.

## 10. Question lifecycle

Recommended V1.3 lifecycle:

**QUESTION IDENTIFIED**
→ classify subject and scope
→ bind to legitimate owner/research programme
→ investigate/develop/test
→ update current state
→ one of:

- REMAINS OPEN;
- DECOMPOSED;
- ARCHITECTURALLY ADDRESSED / VALIDATION OPEN;
- READY FOR TESTING;
- RESOLVED AT DEFINED LEVEL;
- RETIRED;
- PREMISE REJECTED;
- OUT OF SCOPE;
- SUPERSEDED;
- PERMANENT ADVERSARIAL QUESTION.

When a question ceases to be live, Historical preserves its prior states through repository/version succession.

## 11. Migration and legacy-state reconciliation

The Open Questions corpus is likely to contain stale status because V1.2 continued developing after individual question entries were written.

This makes it another target for the early V1.3:

**Legacy Architecture State and Graduation Reconciliation Audit**

That audit should include a **Question-State Reconciliation Pass** asking:

- Has later architecture already answered this question?
- Has the question been decomposed?
- Did an answer become operational but the register remain open?
- Did a supposedly closed question reopen through later evidence?
- Is validation still genuinely open?
- Does the question now belong to a newly recognised domain?
- Is an apparent question actually a missing system/domain gap?
- Is the current wording based on an obsolete architecture?

> **Stale Open Status != Current Uncertainty**

> **Stale Closed Status != Permanent Resolution**

## 14. V1.3 root recommendation

A root-visible `09_Open_Questions` can remain because discoverability of uncertainty is valuable.

It should be substantially simpler than V1.2.

Possible structure:

- `README.md`
- `Current Open Questions — Concord V1.3.md`
- optional machine-readable/index form later.

Do not recreate a large Closed Questions archive inside V1.3.

Closed state is already preserved in predecessor repositories and in the current architecture produced by resolved work.

## 15. Finding

The purpose of the V1.3 Open Questions area should be:

> **Show What the Current Concord Still Does Not Know, Has Not Validated, or Has Not Yet Resolved.**

It should not be:
- a duplicate historical audit chain;
- a cemetery of every old question;
- a second development-history archive;
- or a substitute for Research.

The migration therefore consolidates information rather than folders.

> **Migrate the Uncertainty; Archive the Question History.**

This is another direct application of:

> **Migrate the Living Result; Archive the Developmental Path.**
