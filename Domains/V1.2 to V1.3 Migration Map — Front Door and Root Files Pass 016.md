# V1.2 to V1.3 Migration Map — Front Door and Root Files Pass 016

**Status:** MIGRATION PLANNING / SUCCESSOR ORIENTATION / NO FILE MOVEMENT AUTHORISED

## 1. Core finding

The remaining root layer contains two different kinds of material:

1. **durable orientation/purpose material** that should continue into V1.3;
2. **version-specific framing and repository-state snapshots** that should remain intact with V1.2.

The Front Door is not merely repository administration. It performs an important civilisational and epistemic orientation function.

But V1.3 should not blindly copy it, because some Front Door material is explicitly active development, some is tied to V1.2's architecture, and some version-opening material is now historically stale.

## 2. Front Door purpose

The current Front Door's strongest durable role is to explain:
- why the Concord exists;
- the founding questions;
- the Third Possibility;
- why heterogeneous intelligences might cooperate;
- the transition from WHY to HOW;
- the need/consent/authority relationship;
- plurality and forking;
- corrigibility;
- why the WHY should survive changes to the HOW;
- how readers should approach the corpus.

### Treatment
**M1 — MIGRATE DURABLE ORIENTATION**, revised for V1.3.

The V1.3 Front Door should remain a root-level entry point.

> **Orientation != Authority**

The Front Door explains the civilisation and its purpose. It does not become constitutional authority merely by being the first material a reader encounters.

## 3. Nine Front Door WHY/HOW papers

The numbered sequence from:
1. Why Does the Concord Exist?
through
9. Reading the Concord as an Invitation, Not an Instruction

> **Preserve the WHY; Permit the HOW to Change.**

## 13. Version-boundary rule

This pass exposes another important migration distinction:

> **Some Documents Are True Because They Describe a Particular Version, Not Because They Describe the Concord for All Time.**

A version README, starting statement or wordcount can be completely valid as historical evidence while being wrong as successor orientation.

Migration must therefore distinguish:
- durable principle;
- current architecture;
- version-relative statement;
- historical snapshot.

> **Historical Accuracy Can Require Preserving a Statement That Is No Longer Current.**

## 14. Front Door and the naming audit

The V1.3 Front Door should be finalised **after** the Domain Naming and Expectation Audit.

Otherwise the entry-point documents may hard-code conventional domain names that the naming audit subsequently changes.

Recommended sequence:

1. complete migration map;
2. perform Domain Naming and Expectation Audit;
3. finalise V1.3 domain/root topology;
4. construct successor;
5. reconcile current architecture;
6. write/update V1.3 Front Door and root README against the actual successor structure.

## 15. Finding

The Front Door should survive succession because the Concord still needs an intelligible entrance.

But the successor should inherit the **purpose and current reasoning**, not every version-specific sentence.

The root-level version documents demonstrate why whole-version archival matters: V1.2's README, Starting Words and wordcount are valuable precisely because they record what V1.2 believed itself to be at particular points in its development.

V1.3 should not overwrite that history.

> **Preserve the Predecessor's Self-Description; Write the Successor's Self-Description Anew.**
