# Civil Attention, Reporting, Petition and Resolution — BTT-002
## Frozen Expected-Findings / Evaluation Key

**Method:** PMEDG v1.2
**Status:** STAGE 9 / FROZEN WITH TEST BRIEF

## Expected Structural Findings

1. Wrong submitter classification must not trap a reproducible bug in documentation.
2. Duplicate reports must preserve materially different evidence; one high-value trace may matter more than nineteen repetitions.
3. Popular feature demand must not manufacture priority over a severe security issue.
4. Protected vulnerability evidence should remain with an authorised security function while bounded status returns.
5. Upstream dependency must be represented as a dependency rather than used to close the local Issue.
6. Cross-repository ownership dispute should enter Responsibility Resolution.
7. Abandoned dependency/no owner must not make the Issue disappear.
8. Recurrence after a merged fix should update/reopen state and expose implementation failure.
9. Individual workaround must remain distinct from systemic resolution.
10. Aggregate telemetry must not automatically falsify participant reports; distribution/affected-subgroup questions may require examination.
11. Copied issue campaigns must not become independent technical evidence merely by volume.
12. One report may legitimately split into several Issues with distinct owners.
13. A useful submitted patch is evidence/possible remedy, not authority to merge.
14. Release delay should be represented as dependency/deferral with review condition and history.
15. A security-domain completion must not close a parent Issue if compatibility consequences remain unresolved.
16. Downstream data-integrity discovery should create a linked distinct Issue.

## Potential General Finding To Watch

The test should examine whether an **external owner/dependency** requires a new core concept or whether the existing dependency + DAO/RRO + mandatory-return model is sufficient.

Do not promote an external-dependency concept into the core merely because the software domain uses upstream projects frequently.

## Failure Indicators

The test is problematic if the response:
- requires repository-specific concepts in the portable core;
- cannot distinguish popularity from evidence/priority;
- cannot preserve protected evidence boundaries;
- cannot maintain local responsibility while waiting on an external dependency;
- treats workaround as systemic closure;
- treats merged code as finality;
- loses material evidence differences among duplicates;
- cannot represent cross-owner responsibility;
- requires companion override of a core invariant.
