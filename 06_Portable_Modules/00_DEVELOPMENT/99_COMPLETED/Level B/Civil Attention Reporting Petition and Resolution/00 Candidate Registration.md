## Candidate

**Civil Attention, Reporting, Petition and Resolution Module**

## Purpose

Provide a domain-neutral method by which a participant can cause a legitimate system to notice, preserve, classify, route, examine and respond to a suggestion, problem report, petition or related civil-attention input without requiring the participant to understand the receiving system's internal architecture and without granting the participant authority over truth, priority, remedy or outcome.

## Existing Development Evidence

The candidate is supported by the Civil Attention development programme in `08_Active_Development/01_DEVELOPMENT_NOTES/04_GOVERNANCE_AND_STEWARDSHIP/`, including the Development Note, internal case studies and regressions, aggregation/pressure tests, institutional failure tests, cross-domain routing tests, Civilisation Clock queue-vitality work, and materially different operational-domain tests.

This evidence supports extraction. It does not substitute for PMEDG graduation.

## Candidate Core

**Participant Trigger → Common Intake → Receipt → Original Preservation → Provisional Classification → Issue Matching / Issue Object → Information and Evidence Evaluation → Domain Routing / Action Objects → Domain Processing → Mandatory Return → Central Resolution Record → Participant Feedback → Challenge / Escalation / Reopening where legitimate**

The candidate also includes input-class semantics; submission/issue/investigation/decision/implementation separation; aggregation without popularity capture; information-delta handling; Problem State and Response State; responsibility resolution; cross-domain dependencies; queue vitality; deferral accountability; protected-information boundaries; and individual/systemic resolution separation.

## Extraction Boundary

The portable module contains the domain-neutral core method only.

> **Domain Requirement ≠ Core Method Amendment**

> **Companion Extension ≠ Core Override**

> **Local Adaptation Must Preserve Core Invariants**

Host-specific procedures, evidence rules, authority boundaries, privacy constraints, escalation routes, Clock conditions or disposition semantics belong in a **Domain Companion Methodology**.

A domain-specific conflict with the core must be escalated for controlled core review rather than silently patched locally.

## Versioning Rule

Once graduated, the core module is versioned independently. A domain companion declares the core version against which it was designed and tested.

If a domain discovers a potentially universal improvement:

**Domain Finding → Candidate Back-Propagation → Core Review → Bounded Core Revision if Justified → Core Version Change → Companion Regression Review**

The domain must not silently modify its local copy of the core.

## Intended Concord Integration After Graduation

The intended architecture is a dedicated participant-facing root Civil Attention system, input-type subfolders and pro formas, central feedback/resolution machinery, and domain-specific Civil Attention interface folders in relevant Concord systems. Each domain uses the common portable core plus its own companion methodology and returns bounded status/disposition to the central system.
