## 1. Purpose

After BTT-002 had been frozen, a further distinction was identified:

> A legitimate need and function may justify bounded permission to use a private space without granting authority over that space.

Example:

A delivery driver may reasonably need to enter or temporarily use a private driveway to perform a delivery. That does not give the driver authority over the driveway, permission to exclude the owner, or general permission to occupy it for unrelated purposes. When the delivery function is completed, the function-derived permission normally ends.

Because this insight appeared after a handover and after CWA extraction, ESCP requires source resolution before treating it as new architecture.

---

## 2. ESCP result

A direct review of the wider source corpus found that this architecture already exists in unusually explicit form in:

**Fractal Permission Architecture — Context, Function and Minimum Necessary Access Across Public, Private and Safe Spaces**

The source uses essentially the same residential-property and delivery-worker example.

Therefore:

> **This is not a newly discovered Concord principle. It is a source-recovery event exposing an extraction deficit in CWA.**

The frozen BTT-002 brief and expected-findings key MUST remain unchanged.

The blind response is also preserved unchanged.

# 3. Recovered source architecture

The source explicitly distinguishes spatial classification from access classification:

> **Spatial Classification ≠ Access Classification**

A private property can remain private while supporting different legitimate permission relationships for different participants and functions.

It states:

> **Permission to Enter ≠ Permission to Use**

> **Permission for One Function ≠ Permission for Unrelated Functions**

The source directly gives the example:

- a delivery worker may enter a driveway to deliver a parcel;
- this does not create general permission to remain on the property.

It names the mechanism:

> **Function-Derived Permission**

and defines it as a limited permission arising because a legitimate function reasonably requires a particular interaction with a space.

---

# 4. Minimum Necessary Permission

The recovered architecture contains the full chain:

**Legitimate Function**  
→ **Required Interaction**  
→ **Required Spatial / Informational / Behavioural Access**  
→ **Minimum Necessary Permission**  
→ **Function-Bounded Activity**  
→ **Function Completion**  
→ **Permission Termination**

Its general principle is:

> **Where access or activity is justified by a particular function, the resulting permission should normally be limited to the minimum scope reasonably necessary to perform that legitimate function.**

This is explicitly called:

> **Minimum Necessary Permission**

The architecture is parallel to Minimum Necessary Authority but is not identical to it.

For governance:

**Legitimate Objective → Required Function → Need for Authority → Minimum Necessary Authority → Bounded Contextual Authority**

For ordinary civil access:

**Legitimate Function → Required Interaction → Need for Permission → Minimum Necessary Permission → Bounded Contextual Access**

This distinction is directly relevant to CWA and PRR.

---

# 5. Permission does not create authority

The recovered source makes clear that permission is not a transfer of control.

A participant may possess permission to:

- approach;
- traverse;
- enter;
- remain;
- observe;
- interact;
- use;
- inspect;
- record;
- modify;
- remove;
- deliver;
- retrieve;
- supervise;
- exclude;
- authorise;

but possession of one permission does not imply possession of the others.

Thus:

> **Access ≠ Single Permission**

A delivery driver may have **Approach + Traverse + Enter/Use-for-delivery + Brief Remain** without having:

- general occupation;
- unrelated use;
- exclusion;
- control;
- delegation;
- authorisation of others.

This supports the additional CWA distinction:

> **Functional Permission ≠ Contextual Authority**

and:

> **Permission to Use ≠ Authority to Control**

These formulations are a synthesis of the recovered permission architecture and CWA's existing authority distinctions.

---

# 6. Reasonableness

Reasonableness is not incidental in the source.

The recovered principle states that a function-derived permission exists only where the legitimate function **reasonably requires** the interaction and extends only as far as **reasonably necessary**.

The source's implied-permission rule is:

> **Where a function is ordinary, legitimate, reasonably expected and requires limited access to perform, a bounded contextual permission may be implied unless it has been explicitly restricted or conflicting rights and circumstances require otherwise.**

This prevents “need” from becoming self-justifying.

The chain should therefore be represented as:

**Legitimate Function**  
→ **Genuine Functional Need**  
→ **Reasonably Necessary Interaction**  
→ **Minimum Necessary Permission**  
→ **Function-Bounded Use**  
→ **Function Completion / Basis Ends**  
→ **Permission Terminates**

A claimed need alone is insufficient.

---

# 7. Implied permission

The source explicitly recognises **Implied Permission**.

Ordinary civil life does not require a postal worker to negotiate a new agreement before approaching every front door.

However:

> **Implied Permission Should Be Function-Bounded.**

and:

> **Function Completion Should Normally Terminate Function-Derived Permission.**

Therefore implied permission is not a general licence.

The permission remains bounded by:

- participant;
- action;
- space;
- function;
- conditions;
- time;
- applicable rules;
- explicit restrictions;
- higher-order rights;
- current context.

# 8. Driveway example

The driveway case can be represented as:

### Ordinary delivery

**Private Driveway**  
+ **Delivery Driver**  
+ **Legitimate Delivery Function**  
+ **Reasonable Need to Approach/Stop**  
→ **Implied Minimum Necessary Permission**  
→ **Enter / Traverse / Temporarily Stop as Required for Delivery**  
→ **Delivery Completed**  
→ **Permission Terminates**

The permission does not include:

- indefinite occupation;
- unrelated parking;
- recreational use;
- storage;
- exclusion of the owner;
- control of the driveway;
- permission to authorise unrelated third-party use.

### Unrelated long-term vehicle storage

A commercial parking operator placing a customer's vehicle on an unrelated private driveway for long-term storage cannot derive permission merely from its own commercial function.

Its business function does not create a legitimate functional relationship requiring use of that homeowner's driveway.

Therefore:

**Commercial Parking Function**  
+ **Convenient Private Driveway**  
≠ **Function-Derived Permission**

The architecture distinguishes:

> **A function may explain why an actor wants access without establishing a legitimate basis for that access.**

This is important because otherwise any actor could manufacture permission by defining a function that benefits from another participant's property.

---

# 9. Permission expiry and abuse boundary

The recovered architecture provides a clear transition condition.

Where permission exists only because of a particular function:

> **Function Completion Should Normally Terminate Function-Derived Permission.**

The source also states:

> **Context Termination Should Terminate Context-Derived Permissions Unless Another Legitimate Basis Persists.**

This creates two different abuse cases:

### A. No legitimate permission ever existed

The actor's function did not legitimately require use of this participant's space.

**No Valid Functional Basis → No Function-Derived Permission**

### B. Permission initially existed but expired

**Valid Function-Derived Permission → Function Completed / Abandoned → Permission Terminates → Continued Use Lacks That Permission Basis**

This is a much cleaner architectural boundary than treating “access” as a single binary state.

The legal remedy remains jurisdiction-dependent and belongs outside CWA unless an applicable legal framework supplies it.

---

# 10. Rule provenance

The source also warns that permission may derive from different bases:

- legal requirement;
- owner/steward rule;
- contractual condition;
- relationship permission;
- cultural convention;
- contextual inference;
- emergency necessity.

> **Rule Content ≠ Rule Source**

CWA should therefore record the **basis** of permission rather than merely stating ALLOWED.

An implied cultural permission and an explicit contractual licence may permit similar physical actions while having different revocation, remedy and dispute implications.

---

# 11. Permission vector

The recovered source provides a useful Contextual Permission Vector:

**Approach | Traverse | Enter | Remain | Observe | Interact | Use | Inspect | Record | Modify | Remove | Exclude | Authorise**

CWA need not require this full vector for every ordinary interaction.

But where ambiguity matters, it prevents one permission from silently expanding into another.

For the driveway:

**Approach: YES**  
**Traverse: YES, as reasonably required**  
**Enter/Use: YES, for delivery**  
**Remain: YES, only as reasonably required**  
**Unrelated Use: NO BASIS**  
**Exclude Owner: NO**  
**Authorise Others: NO**  
**Control: NO**

# 12. Relationship to PRR

This recovery fills an important step between:

**No Permission**

and:

**Authority**

PRR should not ask only whether an actor has authority.

It should first ask whether the function requires merely:

- ordinary public access;
- explicit permission;
- implied/function-derived permission;
- relationship-derived permission;
- contractual permission;
- emergency permission;

before escalating to authority.

This aligns with the Authority Justification Chain principle:

> **Legitimate Function does not imply special authority is required.**

A function that can be performed through ordinary bounded permission should not manufacture authority.

# 14. Required CWA revision

After preserving BTT-002 provenance, CWA should add a dedicated **Functional Permission and Minimum Necessary Permission** section containing at minimum:

1. **Functional Permission ≠ Contextual Authority**
2. **Permission to Enter ≠ Permission to Use**
3. **Permission for One Function ≠ Permission for Unrelated Functions**
4. **Permission to Use ≠ Authority to Control**
5. legitimate function + genuine need + reasonable necessity;
6. minimum necessary permission;
7. implied permission where ordinary, legitimate and reasonably expected;
8. permission vector / action-specific permission;
9. temporal and purpose scope;
10. function completion normally terminates function-derived permission;
11. explicit restriction/revocation subject to wider rights/law;
12. provenance of permission basis;
13. function cannot self-legitimate merely because access would be useful.

PRR should also include a **Permission-Before-Authority Gate**.
