## 2. Source problem

The Civil State Map asks:

> **What is the current developmental condition of the civilisation?**

Its purpose is not to score how advanced a civilisation is. It represents uneven developmental state so that presence, maturity, sufficiency, dependency, consequence, uncertainty and active work are not collapsed into one judgement.

The portable problem is broader:

> **How can a complex system represent the current developmental condition of required functions in context without confusing presence with maturity, maturity with sufficiency, local absence with system absence, dependency blockage with absence, or the resulting state description with authority over what must happen next?**

Potential hosts include:

- engineering programmes;
- research organisations;
- software/platform architecture;
- safety and assurance systems;
- institutional capability maps;
- long-duration projects;
- distributed organisations;
- AI-agent ecosystems;
- infrastructure portfolios;
- other complex systems with uneven capability development.

## 3. Distinct portable owner

The portable owner is:

> **function/state identification + context-sensitive presence + maturity + sufficiency representation + dependency/blocker state + consequence/exposure + uncertainty/dispute + evidence/provenance + freshness + bounded response candidacy**

It does **not** own:

- the host's complete topology;
- discovery of every dependency;
- substantive domain authority;
- resource allocation;
- priority selection;
- remediation execution;
- universal maturity criteria;
- universal consequence scoring;
- the truth of every underlying datum.

This is distinct from STRA, KCS, KCS Change Propagation, AUR and the full Civilisation Clock.

## 4. Portable kernel

The source conclusion gives the strongest compact transformation:

> **Required Function → Current State → Sufficiency → Dependency → Consequence → Development Need**

For portable extraction this should be bounded as:

> **Identify required function → establish context → represent presence → assess applicable maturity dimensions → determine context-relative sufficiency → represent dependencies/blockers → record consequence/exposure and uncertainty → classify unresolved state → produce bounded review/development candidacy → preserve evidence/history**

The final step remains candidacy, not authority.

## 5. Core state model

Source model:

**SM(t) = <N, P, M, Q, D, C, U, A, R>**

Portable interpretation:

- **N** — represented required functions/units;
- **P** — presence state;
- **M** — maturity state;
- **Q** — context-relative sufficiency;
- **D** — dependency/blocker state;
- **C** — consequence/exposure;
- **U** — uncertainty/dispute;
- **A** — active work/development state;
- **R** — evidence, provenance, freshness and review state.

The model synthesises evidence; it does not own every underlying datum.

## 6. Map/model boundary

Source invariant:

> **SM(t) ≠ Civilisation(t)**

Portable invariant:

> **Represented State ≠ Complete System Reality**

A missing entry may indicate incomplete representation. An incorrect entry may reflect model error. A stale entry may once have been correct.

Therefore correction, challenge, competing evidence, UNKNOWN and DISPUTED are structural requirements.

## 7. Unit-of-assessment boundary

The source assesses a required civil function or legitimate architectural unit rather than a document.

Portable rule:

Before consequential assessment:

1. identify the required function/unit;
2. identify legitimate owner/distributed suppliers where relevant;
3. identify interfaces;
4. identify context;
5. source-resolve apparent omissions where the host permits.

An artefact may be evidence about a function without being the function itself.

This interfaces directly with Architectural Unit Resolution but does not require SMM to own AUR.

## 8. Presence

Minimum source states:

- PRESENT_EXPLICIT
- PRESENT_DISTRIBUTED
- INTERFACE_SATISFIED
- PARTIAL
- DEPENDENCY_BLOCKED
- CANDIDATE_ABSENT
- UNKNOWN
- DISPUTED
- NOT_APPLICABLE

Portable invariant:

> **Presence ≠ Maturity**

Also:

> **Dependency-Blocked ≠ Absent**

> **Locally Missing ≠ Systemically Absent**

## 9. Maturity

The source uses ten common maturity probes:

- bounded scope;
- legitimate/non-self-justifying authority;
- temporal revision/exit/termination;
- contestability/correction/repair;
- participant standing/agency;
- asymmetry/anti-capture compensation;
- effective access;
- function-over-form/replaceability;
- recursive review;
- provenance/learning.

These are Concord-derived common probes and should **not** automatically become universal mandatory maturity dimensions in the portable module.

Portable extraction should instead distinguish:

1. **host/domain maturity dimensions** — legitimately supplied by the host/domain;
2. **candidate cross-domain probes** — reusable prompts that may be applicable but require applicability testing.

Minimum dimension states remain strongly portable:

- SATISFIED_INTERNAL
- SATISFIED_INTERFACE
- PARTIAL
- UNSATISFIED
- DEPENDENCY_BLOCKED
- UNKNOWN
- DISPUTED
- NOT_APPLICABLE

## 10. Context and sufficiency

The source correctly makes maturity consequence-sensitive.

A context may include:

- deployment domain;
- consequence class;
- affected participants/users;
- authority exercised;
- scale;
- substrate/platform;
- operational/experimental mode;
- reversibility;
- duration;
- current exposure.

Portable sufficiency asks:

> Is this function sufficiently developed for this declared context and consequence?

Candidate states:

- SUFFICIENT
- CONDITIONALLY_SUFFICIENT
- INSUFFICIENT
- BLOCKED
- UNKNOWN
- DISPUTED
- NOT_APPLICABLE

Core boundary:

> **Maturity ≠ Context-Relative Sufficiency**

A capability can be adequate for advisory use and inadequate for consequential operational use.

## 11. No universal maturity score

The source rejects a single maturity percentage.

This transfers strongly.

A multidimensional system may be strong in one property and weak in another. Collapsing the vector can hide the material deficit.

Portable default:

> **State Vector ≠ Universal Score**

A host may define a justified aggregate for a bounded use, but SMM should not require one.

## 12. Contiguous development vs feature exposure

Source distinction:

- **contiguous developmental level** — highest level reached without unresolved applicable lower requirement;
- **feature exposure** — highest higher-order capability observed anywhere.

Portable value:

> **Higher Feature Exposure ≠ Lower Requirement Satisfaction**

This is useful where hosts employ ordered developmental/assurance levels, but should remain optional because not every host has a meaningful hierarchy.

## 13. Dependencies and interfaces

The source consumes KCS dependency records. The portable module should instead consume a generic dependency/state interface.

For each assessed function where material:

- prerequisites;
- blocking prerequisites;
- downstream dependents;
- alternatives;
- confidence;
- failure consequence;
- freshness.

SMM does not own the dependency graph.

> **Dependency State Representation ≠ Dependency Discovery Ownership**

- DEVELOPMENTAL_GAP
- INTEGRATION_INTERFACE_GAP
- DEPENDENCY_BLOCKED
- REPRESENTATION_GAP

## 15. Response candidacy

Source mapping:

- SATISFIED → NO_ACTION
- REPRESENTATION_GAP → IMPROVE_MAP_OR_EVIDENCE
- INTEGRATION_INTERFACE_GAP → INTERFACE_OR_INTEGRATION
- DEVELOPMENTAL_GAP → DEVELOP_EXISTING_OWNER
- TRUE_ARCHITECTURAL_GAP → NEW_ARCHITECTURE_CANDIDATE
- DEPENDENCY_BLOCKED → RESOLVE/DEVELOP UPSTREAM
- UNKNOWN → INVESTIGATE
- DISPUTED → PRESERVE_DISPUTE_AND_REVIEW

Portable extraction should preserve these as **candidate response classes**, not automatic commands.

> **State Description ≠ Permission**

> **Development Need ≠ Authority**

## 16. Consequence/exposure

Portable consequence/exposure record may include:

- severity if unresolved;
- probability/frequency where legitimately estimable;
- affected users/participants/functions;
- reversibility;
- time sensitivity;
- current deployment/exposure;
- safeguards;
- uncertainty.

Important source safeguard:

> Low-connectivity high-consequence deficits must remain visible.

This prevents centrality from becoming the sole prioritisation heuristic.

## 17. Ownership

The source records legitimate owner, distributed suppliers, interface suppliers, fallback, disputed ownership and unknown ownership.

Portable boundary:

> **State Map Cannot Create Ownership**

If ownership is unknown or disputed, SMM preserves that state rather than assigning a convenient actor.

## 18. Evidence, confidence and freshness

Every consequential state claim should link to evidence/provenance.

Operational records should support where material:

- state date;
- evidence date;
- last review;
- next review;
- changed-since-review;
- stale-state flag.

> **Stale ≠ False**

Staleness creates reconsideration pressure, not automatic negation.

## 19. Active work state

The source tracks active development so a scheduler does not repeatedly select work already underway.

This is portable as optional work-state metadata. Candidate states may include:

- NONE
- INVESTIGATING
- SOURCE_RESOLUTION
- FROZEN_FOR_TEST
- DEVELOPMENT_ACTIVE
- EVALUATION
- AWAITING_INTEGRATION
- INTEGRATED_AWAITING_RETEST
- RETEST
- HOLD
- CLOSED

A host may map these to its own workflow vocabulary.

## 20. Minimum portable record

Candidate:

**SMR = <ID, function, owner, context, presence, maturity, sufficiency, dependencies, blockers, interfaces, consequence/exposure, unresolved requirements, gap/state class, candidate response, evidence/provenance, confidence, uncertainty/dispute, freshness/review, active-work state>**

Not every field must be populated when legitimately unknown or inapplicable; UNKNOWN and NOT_APPLICABLE must remain representable.

## 21. State transition/history

Portable transition:

**SM_t → SM_t+1**

Material transitions should preserve:

- what changed;
- why;
- evidence;
- evaluator/process;
- downstream review effects where known;
- unresolved disagreement.

> **Current State ≠ Erasure of Prior State**

KCS is one possible provider but not required.

## 22. Update triggers

A record may require reconsideration when:

- underlying function/architecture changes;
- dependency changes;
- interface changes;
- new evidence appears;
- failure occurs;
- correction propagates;
- deployment context changes;
- materially affected user/participant class changes;
- review becomes overdue;
- prediction/test fails;
- legitimate challenge is raised.

State Triggered Review Architecture may be one portable mechanism for implementing such review triggers, but SMM does not depend on STRA specifically.

## 23. Operational evidence

The source family contains more than conceptual architecture.

The Initial Concord V1.2 State Map populated L0-L3 and demonstrated that the model could distinguish:

- occupied functions from demonstrated absence;
- present/distributed supply;
- developmental unevenness;
- dependency blockage;
- integration residuals.

The CCSSL prospective work froze queue rules before candidate inspection and later reported architectural support for six frozen downstream predictions, with no contradiction at architectural level.

State Map 001C also distinguished three bottleneck classes:

- functional maturity bottleneck;
- integration maturity bottleneck;
- synthesis-state bottleneck.

Later canonical State Map updates were used as frozen inputs to Clock validation and preserved ordinary residual work without forcing further meta-system development.

This is meaningful internal prospective evidence, but not independent external validation.

## 24. Portable failure modes

Candidate failure modes:

**SMM-F1 — False completeness**  
Unrepresented function appears complete or irrelevant.

**SMM-F2 — False maturity**  
Documentation, formalisation or labels substitute for capability.

**SMM-F3 — Presence/maturity collapse**  
Presence is treated as adequate development.

**SMM-F4 — Maturity/sufficiency collapse**  
General maturity is treated as sufficient for every context.

**SMM-F5 — Locality error**  
Locally absent capability is treated as systemically absent.

**SMM-F6 — Interface blindness**  
Externally/interface-supplied capability is missed.

**SMM-F7 — Dependency blindness**  
Blocked downstream function is treated as locally deficient.

**SMM-F8 — Centrality bias**  
Highly connected items dominate while low-connectivity high-consequence deficits disappear.

**SMM-F9 — Staleness**  
Old state drives current judgement.

**SMM-F10 — Ownership fabrication**  
The map assigns a convenient owner.

**SMM-F11 — Authority capture**  
State classification becomes command/resource authority.

**SMM-F12 — Score collapse**  
Multidimensional state is hidden by an unjustified scalar score.

**SMM-F13 — Uncertainty erasure**  
UNKNOWN/DISPUTED is forced into binary classification.

**SMM-F14 — Anti-gaming failure**  
Labels/prose/state manipulation improves apparent maturity without capability.

**SMM-F15 — History erasure**  
Current state destroys provenance of prior states and corrections.

**SMM-F16 — Perpetual-development bias**  
The map can never represent adequate sufficiency or a legitimate stop/hold state.

## 25. External interfaces

Portable SMM requires bounded interfaces to:

- required-function/unit definition;
- context definition;
- evidence/provenance;
- dependency/blocker state where material;
- ownership/supplier state;
- host maturity criteria;
- host sufficiency thresholds;
- consequence/exposure evidence;
- review/update mechanism;
- legitimate response/priority process.

It does not require Concord's CDT, KCS or Civilisation Clock by name.

- the specific V1.2 baseline;

Preserve the underlying distinctions and interfaces.

## 27. Extraction risks

The largest extraction risk is over-porting the ten Concord maturity dimensions as universal criteria.

The second is accidentally turning a descriptive state map into a priority/resource-allocation mechanism.

The third is treating the State Map as a completeness oracle.

The portable specification must explicitly prevent all three.
