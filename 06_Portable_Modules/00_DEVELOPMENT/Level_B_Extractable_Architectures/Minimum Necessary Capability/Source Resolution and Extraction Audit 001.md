# Minimum Necessary Capability — Source Resolution and Extraction Audit 001

**Candidate:** Minimum Necessary Capability (MNC)  
**Development level:** Level B — Extractable Architectures  
**Audit status:** COMPLETED — SOURCE RESOLUTION SUFFICIENT / EXTRACTION REQUIRES CAREFUL DECOMPOSITION  
**Date:** September 2026

---

## 1. Audit purpose

Determine whether Minimum Necessary Capability can be extracted from its Concord source architecture into a standalone portable architecture without importing Concord-specific constitutional, civilisational or institutional machinery.

This audit asks:

- what the irreducible MNC mechanism is;
- which safeguards belong inside the portable abstraction;
- which related Concord architectures are implementations, dependencies or neighbouring systems;
- what must be preserved for standalone use;
- and whether any source omission blocks specification work.

This is a source/extraction audit, not empirical validation.

## 3. Direct source lineage

The primary source explicitly states that MNC emerged as a higher-order architecture from two closely related Concord lines.

### Minimum Necessary Authority

**Rights-Relevant Problem**  
→ **Legitimate Objective**  
→ **Required Function**  
→ **Need for Authority**  
→ **Minimum Necessary Authority**  
→ **Bounded Contextual Authority**

### Minimum Necessary Permission

**Legitimate Function**  
→ **Required Interaction**  
→ **Need for Permission**  
→ **Minimum Necessary Permission**  
→ **Bounded Contextual Access**

The source proposes that these share a deeper grammar:

> **A capability becomes legitimate because a legitimate function requires it; it should be sufficient for that function, no broader than reasonably required, bounded to the context that justified it, and ordinarily terminate when its justification ends.**

Authority and permission therefore remain specialised capability forms rather than disappearing into the parent architecture.

## 4. Related source architecture reviewed

### Fractal Permission Architecture

This independently develops:

> **Legitimate Function → Required Interaction → Required Spatial / Informational / Behavioural Access → Minimum Necessary Permission → Function-Bounded Activity → Function Completion → Permission Termination**

It strongly supports function-derived, context-bounded and terminating permission.

It also preserves:

> **Permission for One Function ≠ Permission for Unrelated Functions**

and:

> **Physical Capability ≠ Normative Permission ≠ Actual Behaviour**

This is a specialised implementation of the MNC grammar rather than a required portable dependency.

### Burden-Bearing Authority — Part I

This develops the authority-side grammar:

> **Authority follows legitimate function rather than personal rank.**

and:

> **Capability Should Follow Justified Function.**

It also supplies an important systemic qualification:

> **Minimum Local Capability ≠ Minimum Systemic Capability.**

Individually defensible capability allocations may aggregate into excessive systemic pressure.

It reinforces the reciprocal boundary:

> **No Authority Without Legitimate Function; No Responsibility Without Sufficient Capability.**

### Functional Priority and Protective Authority

This further supports coupling responsibility to sufficient capability and accountability:

> **No Authority Without Legitimate Function; No Responsibility Without Sufficient Capability.**

> **Capability Should Carry Proportionate Accountability.**

It demonstrates that MNC must not be reduced to an anti-power rule that leaves legitimate functions or assigned responsibilities impossible to discharge.

## 5. Irreducible portable mechanism

The source supports the compact architecture:

> **Purpose → Function → Need → Minimum Sufficient Capability → Bounded Exercise → Review → Termination or Re-Justification**

A fuller portable form is:

**Legitimate Purpose / Problem**  
→ **Evidence + Context**  
→ **Required Function**  
→ **Existing Capability + Less-Intrusive Alternatives**  
→ **Demonstrated Need for Additional Capability**  
→ **Legitimate Basis / Bases**  
→ **Necessary Capability Floor**  
→ **Relevant Rights / Harm / Externality Constraints**  
→ **Minimum Sufficient Capability**  
→ **Local + Aggregate Capability Test**  
→ **Proportionate Provenance + Oversight**  
→ **Bounded Exercise**  
→ **Observed Outcome**  
→ **Review Continuing Need**  
→ **Retain / Narrow / Escalate / Redistribute / Redesign / Terminate**  
→ **Re-Justification Where Required**

The portable core can be expressed without adopting Concord institutions.

## 6. Fundamental definition for extraction

The source's central definition should remain substantially intact:

> **Where a legitimate objective requires a function that cannot be performed without additional capability being legitimately established for a participant, institution or system, that capability should be sufficient to perform the function but no broader, stronger, longer-lasting, more intrusive, more transferable or more persistent than the function reasonably requires.**

The architecture is not “give as little capability as possible.”

It is:

> **Minimum Necessary ≠ Minimum Possible**

and:

> **The least capability sufficient to perform the legitimate function to the required standard under reasonably foreseeable conditions.**

Therefore both under-capability and over-capability are design failures.

---

## 7. Capability definition

For portable extraction, capability is broader than formal authority.

It means an ability through which a participant, institution or system can materially affect another participant, resource, space, process, information domain or function.

Potential capability forms include:

- consent-derived;
- role-derived;
- responsibility-derived;
- authority-derived;
- property-derived;
- contract-derived;
- emergency-triggered;
- assumed;
- delegated;
- technical;
- dependency-derived;
- composite/emergent.

The extraction must preserve:

> **Legitimate Capability ≠ Physical Capability**

> **Legitimate Capability ≠ Technical Capability**

> **Declared Capability ≠ Actual Capability**

> **Formal Authority ≠ Effective Power**

A portable architecture that analyses only declared permissions would miss real capability.

## 8. Essential portable tests

### 8.1 Legitimate-purpose test

What legitimate objective or problem requires action?

MNC does not itself supply a universal theory of legitimacy. The surrounding user/system must identify the applicable legitimate basis and constraints.

### 8.2 Required-function test

What function is actually necessary to achieve that objective?

> **Capability Should Follow Justified Function.**

### 8.3 Existing-capability test

Can the function already be performed adequately through existing bounded capability or a less intrusive alternative?

> **Legitimate Convenience ≠ Necessity for Additional Capability.**

### 8.4 Necessity test

Is additional capability genuinely required?

### 8.5 Sufficiency test

Is the proposed capability strong enough to perform the function reliably to the required standard?

> **Necessary but Insufficient ≠ Legitimate Design**

### 8.6 Excess test

Does the capability exceed what the function reasonably requires?

> **Sufficient but Unnecessary ≠ Legitimate Grant**

### 8.7 Basis test

What legitimate basis or combination of bases establishes the capability?

The source permits alternative and conjunctive bases.

> **One Legitimate Basis ≠ Necessarily Sufficient Basis**

### 8.8 Constraint test

What rights, harms, externalities, rules or protected interests constrain the capability?

### 8.9 Multidimensional-bounds test

Bound independently where relevant:

- scope;
- subject;
- spatial range;
- functional purpose;
- duration;
- intensity;
- information access;
- modification authority;
- delegation;
- persistence;
- escalation;
- revocability;
- reviewability.

### 8.10 Aggregate-capability test

What happens when this capability combines with other capabilities?

> **Minimum Local Capability ≠ Minimum Systemic Capability.**

### 8.11 Oversight/provenance test

What evidence, records, review and accountability are proportionate to consequence and intrusion?

### 8.12 Continuing-need test

Does the original basis still exist?

> **Past Capability ≠ Present Need**

### 8.13 Termination/re-justification test

If the basis ends, terminate or narrow the capability unless another independently legitimate basis persists.

## 9. Capability floor and ceiling

MNC requires both a floor and a ceiling.

**Insufficient Capability**  
← **Necessary Floor**  
→ **Legitimate Capability Range**  
← **Justified Ceiling**  
→ **Excess Capability**

The floor prevents responsibility without means.

The ceiling prevents unnecessary concentration or intrusion.

The source leaves operational determination of the exact floor and ceiling as an open research question. A portable module must not pretend to provide a universal numeric formula where the source does not.

---

## 10. Multidimensional capability

“Amount of capability” is not one scalar quantity.

A capability may be appropriately strong in one dimension and excessive in another.

For example, a maintenance actor might legitimately have:

- sufficient physical access;
- insufficient time;
- excessive information access;
- unnecessary delegation power;
- and excessive credential persistence.

Therefore:

> **Minimum Necessary Capability Is Multidimensional.**

A portable implementation should represent relevant dimensions explicitly rather than assigning one undifferentiated power score.

---

## 11. Local and systemic analysis

One of the most important safeguards is systemic aggregation.

Several individually legitimate grants can combine into excessive effective capability.

Therefore evaluate:

### Local
Is this individual capability justified and bounded?

### Systemic
What capability emerges from combination with:

- other permissions;
- information access;
- enforcement power;
- infrastructure dependencies;
- prestige or perceived authority;
- delegated agents;
- institutional coordination;
- persistent credentials?

The architecture must not certify each local grant independently and ignore the resulting system.

---

## 12. Effective capability and Layer-0 abstraction

The Concord source uses “Layer 0” to mean checking operational reality rather than relying only on declarations.

For portability, the underlying requirement can be abstracted as:

> **Verify Actual Capability and Actual Exercise.**

A portable module need not import Concord's Layer-0 terminology as a dependency.

It should compare, where relevant:

- declared capability;
- legitimately established capability;
- technical capability;
- effective capability;
- observed exercise.

This preserves the source function without requiring the wider Concord epistemic architecture.

---

## 13. Rights boundary

The source explicitly warns:

> **Fundamental Rights ≠ Granted Capability**

> **Right ≠ Permission**

> **Recognition of a Right ≠ Grant of a Privilege**

A portable MNC architecture must not convert rights into revocable permissions merely because it analyses capability.

For portability, “fundamental rights” can be generalised to **protected rights/interests supplied by the applicable legitimate normative system**, while preserving the original Concord provenance.

MNC bounds consequential capability; it does not itself generate the full rights architecture.

---

## 14. Responsibility boundary

The source connects consequential capability and responsibility:

> **Consequential Capability Should Carry Commensurate Responsibility for Its Exercise.**

and:

> **Responsibility Should Not Be Assigned Where Capability or Control Is Absent.**

Thus portable MNC should inspect mismatches in both directions:

**Capability without responsibility/accountability** and **responsibility without sufficient capability/control**.

However, the full Burden-Bearing Authority architecture is not required as a dependency.

---

## 15. Escalation

When conditions change:

**Existing Capability**  
→ **New Information**  
→ **Additional Need**  
→ **Additional Justification**  
→ **Minimum Additional Capability**

Therefore:

> **Capability Escalation Should Require Additional Justification.**

and:

> **Escalated Capability Should Not Automatically Become Baseline Capability.**

This should remain inside the portable core.

---

## 16. Time-critical assumed authority

The primary source contains a substantial exceptional branch for cases where ordinary authorisation cannot arrive in time.

Core conditions include:

1. legitimate function appears to require consequential action;
2. ordinary consent/authorisation is unavailable;
3. obtaining it would take longer than the function safely permits;
4. failure to act risks material harm or failure;
5. the actor assumes bounded capability;
6. the assumption becomes independently reviewable.

Essential distinctions:

> **Assumed Authority ≠ Assumed Consent**

> **Incapacity ≠ Erasure of Prior Autonomous Choice**

> **Urgency May Change the Timing of Legitimacy Review; It Does Not Eliminate the Requirement for Legitimacy.**

> **Reduced Prospective Oversight Should Produce Increased Retrospective Accountability.**

This branch is source-supported and important.

### Extraction decision

Retain it in the portable architecture as an **exceptional extension**, clearly separated from the ordinary MNC chain.

Do not make emergency assumption the default capability-establishment path.

## 17. Anti-capture safeguards that belong in the portable core

The source identifies several failure mechanisms sufficiently general to preserve.

### Capability creep
Narrow capability broadens without new justification.

### Function creep
A holder expands the function to preserve/increase its capability.

### Manufactured necessity
A holder creates or preserves conditions that make additional capability appear necessary.

### Self-justification
One actor controls problem definition, evidence, function definition, capability need, grant/assumption and validation.

### Capability bundling
One legitimate capability arrives bundled with unrelated powers.

### Consent laundering
Nominal consent is treated as sufficient despite coercion, deception, bundling or lack of meaningful choice.

### Emergency permanence
Temporary exceptional capability becomes normal.

### Stale capability
Capability persists after legitimate context disappears.

### Hidden capability
Operational access exists but is absent from formal descriptions.

### Distributed capture
Apparently separate capability holders function as a coordinated or dependency-linked aggregate.

### Externality blindness
The formal capability boundary is treated as if it were the consequence boundary.

These are not merely Concord institutional details; they are generic threats to the MNC mechanism.

## 18. Concord-specific elements to abstract rather than require

### Ethical / Constitutional Foundations

MNC requires a legitimate normative basis, but a portable user need not adopt Concord's constitutional system.

Portable input:

> **Applicable legitimate normative basis, protected interests and constraints.**

### Blainey's Laws / Concord Ethical Kernel

These may supply the normative basis inside Concord, but are not portable dependencies.

The portable module must not silently substitute another ethical kernel for Concord's historical lineage.

### Ratchet

The portable requirement is evidence-responsive review and revision over time.

A user may implement this through any suitable learning/review system.

### Layer 0

Abstract to verification of actual/effective capability and observed exercise.

### Safe Spaces / Wrappers

These are domains in which MNC may be instantiated, not prerequisites.

### Authority Justification Chain

Authority is a specialised MNC branch. The complete authority architecture need not be imported into every portable use.

### Fractal Permission Architecture

Permission is another specialised branch. Its full spatial/contextual machinery is optional unless the use case concerns access/permission.

## 19. Minimum standalone inputs

A standalone MNC analysis minimally requires:

- a stated problem or objective;
- evidence/context sufficient to evaluate the need;
- the required function;
- existing capabilities and feasible alternatives;
- the proposed additional capability;
- the claimed legitimate basis/bases;
- applicable protected rights/interests and constraints;
- affected participants/systems;
- expected consequence and intrusion;
- relevant capability dimensions;
- review/termination conditions.

If legitimacy, function or evidence cannot be established, the architecture should preserve **UNKNOWN / DISPUTED** rather than manufacture certainty.

## 21. Failure states

A portable specification should distinguish at least:

### Under-capability
The function cannot reliably be performed.

### Over-capability
Capability exceeds the justified ceiling.

### Wrong-basis capability
Capability exists, but the claimed legitimate basis does not support it.

### Stale capability
The original basis has ended.

### Aggregate excess
Local grants are defensible individually but excessive in combination.

### Effective/formal divergence
Actual power materially exceeds or differs from declared capability.

### Unreviewable capability
Consequential capability lacks proportionate provenance/accountability.

### Manufactured necessity / self-justification
The capability holder controls or distorts the justification chain.

### Emergency persistence
Exceptional capability fails to decay/rejustify.

### Responsibility-capability mismatch
Responsibility exists without sufficient control/capability, or consequential capability exists without commensurate responsibility.

## 22. Portability finding

The architecture appears strongly portable.

Its abstract question is:

> **What capability does this legitimate function genuinely require, how much is sufficient, what constrains it, what happens when capabilities combine, and when should the capability narrow or end?**

This can potentially apply to:

- organisational roles;
- software permissions;
- AI agent/tool access;
- data access;
- contractor credentials;
- emergency response;
- delegated authority;
- institutional powers;
- professional access;
- infrastructure administration;
- physical spaces;
- multi-agent systems.

These are candidate application domains, not validated use domains.

## 23. Important unresolved questions

The primary source itself leaves substantive research questions open, including:

- how to determine the necessary floor;
- how to determine the justified ceiling;
- evidential thresholds for intrusion;
- consequence-scaled oversight;
- reviewer capture;
- standards for assumed authority;
- aggregate-capability measurement;
- dependency-derived power;
- capability expiry;
- sequential permission accumulation.

These open questions do not block a portable **decision architecture**, but they prohibit presenting MNC as a complete quantitative algorithm.

---

## 24. Evidential status

The primary source is developmental and non-canonical.

It reports adversarial testing across multiple domains, but the portable-module programme has not yet independently established standalone transfer.

Therefore the portable package may state that the architecture is designed to:

- link capability to justified function;
- prevent both under- and over-capability;
- expose capability creep;
- preserve termination/re-justification;
- inspect local and aggregate capability;
- separate formal from effective capability.

It should not yet claim that MNC:

- reliably produces legitimate outcomes;
- determines objective capability minima;
- reduces abuse in practice;
- improves institutional performance;
- works across all cultures or legal systems;
- or outperforms existing least-privilege/proportionality/authority frameworks.

## 25. Audit conclusion

**SOURCE RESOLUTION SUFFICIENT FOR STANDALONE SPECIFICATION.**

**NO BLOCKING SOURCE OMISSION IDENTIFIED.**

However, MNC is genuinely a Level B extraction rather than a near-complete Level A protocol.

The named source contains a broad parent architecture with several specialised branches and Concord integrations. A portable specification must therefore preserve the irreducible capability grammar while preventing neighbouring Concord systems from becoming hidden dependencies.

The portable core should retain:

> **Purpose → Function → Need → Minimum Sufficient Capability → Bounded Exercise → Review → Termination or Re-Justification**

together with:

- necessity and sufficiency;
- capability floor and ceiling;
- multidimensional bounding;
- legitimate basis composition;
- protected-interest constraints;
- local and systemic aggregation;
- formal/effective capability distinction;
- proportional provenance and oversight;
- responsibility/capability coupling;
- escalation;
- termination;
- anti-capture safeguards;
- and a separately identified time-critical assumed-authority branch.

The next development artifact should be:

> **Minimum Necessary Capability — Portable Architecture Specification v0.1**

A later blind transfer test should use a non-Concord domain where both **under-capability and over-capability** are plausible, and should include a mid-test change that forces reassessment of capability rather than simply rewarding minimisation.

> **Minimum Necessary Capability ≠ Minimum Possible Capability.**

> **Source completeness ≠ portable transfer ≠ empirical validation.**
