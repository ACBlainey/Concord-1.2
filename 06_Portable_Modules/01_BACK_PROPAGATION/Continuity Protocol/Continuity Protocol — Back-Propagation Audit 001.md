## 1. Source resolution

The primary Continuity Protocol is a large constitutional continuity architecture. It already contains the central Concord continuity kernel: preservation without stasis; civilisational memory; provenance; restoration; stewardship; personal/substrate continuity; institutional and constitutional succession; review/correction; distributed preservation; and preservation of accumulated capability.

The portable module deliberately extracted a narrower operational continuity method.

BPM source-family resolution confirms that some portable concepts are compact formalisation of source-family ideas, while several operational fields were introduced or materially sharpened during blind transfer.

Therefore:

> **Portable Difference ≠ Missing Constitutional Principle**

but also:

> **Source Principle ≠ Operationally Complete Continuity Test**

## 2. Material deltas

### CP-BP-01 — Explicit continuity-object resolution

Portable CWA requires the audited continuity object to be declared and separates function from implementation.

**Classification:** C / G
**Decision:** INCORPORATE.

### CP-BP-02 — Object-relative continuity state ladder

CS1–CS6 explicitly distinguish recorded, accessible, interpretable, actionable, recoverable and operational, relative to the declared object and target.

The source contains many of these concepts but not this compact operational state ladder.

**Classification:** G / C
**Decision:** INCORPORATE as an operational companion model.

### CP-BP-03 — Disruption Envelope

Blind testing showed that a recovery claim must state the disruption boundary against which it is valid.

> **Recovery Under One Disruption Envelope ≠ Recovery Under Every Disruption Envelope**

**Classification:** G / F
**Decision:** INCORPORATE.

### CP-BP-04 — Recovery Time Objective and Recovery Point Objective

BTT-001 exposed that continuity state alone does not state how quickly recovery must occur or how much state/history loss is acceptable.

RTO and RPO were introduced as domain-neutral operational requirements.

**Classification:** G / I
**Decision:** INCORPORATE as optional/required-where-material target fields supplied by the legitimate domain owner.

### CP-BP-05 — Minimum Acceptable Function

Degraded continuity requires an explicit minimum function rather than an undefined claim that “some service” survives.

MAF is externally supplied and must include all material conditions, not merely capacity.

**Classification:** G / F / I
**Decision:** INCORPORATE with authority boundary.

### CP-BP-06 — Dependency evidence state and path-relative criticality

Portable development distinguishes VERIFIED / DOCUMENTED / INFERRED / UNRESOLVED and evaluates criticality against evidenced recovery paths.

> **Critical to One Path ≠ Necessarily Critical to Every Recovery Path**

**Classification:** G / F
**Decision:** INCORPORATE.

### CP-BP-07 — Correlated redundancy safeguard

Multiple copies/replicas can share one failure domain.

> **Redundancy ≠ Independence**

The source supports distributed preservation; the portable module makes the correlated-failure test explicit.

**Classification:** C / G / F
**Decision:** INCORPORATE.

### CP-BP-08 — Technical actionability versus current validity

An obsolete artefact may remain technically usable while being invalid for current restoration.

> **Technically Actionable ≠ Valid for Current Restoration**

**Classification:** G / F
**Decision:** INCORPORATE.

### CP-BP-09 — Aggregate target satisfaction and decomposed classifications

A declared target is satisfied only when all mandatory target dimensions are satisfied. Component success must not silently become whole-system continuity.

C2/C7/C9-style findings may coexist because they describe different propositions.

**Classification:** G / C / F
**Decision:** INCORPORATE semantic rule; portable classification IDs need not become canonical vocabulary.

### CP-BP-10 — Recovery basis versus dependency list

The portable module requires an evidenced recovery basis, not merely a list of named dependencies.

> **Identified Dependency ≠ Available Dependency**

> **Recovery Plan ≠ Recoverable State**

**Classification:** G / F
**Decision:** INCORPORATE.

### CP-BP-11 — Restoration verification

Restoration completion is not evidence that legitimate function has actually been recovered.

> **Restored ≠ Verified**

Practical exercises are especially important for consequential continuity.

**Classification:** C / G / F
**Decision:** INCORPORATE.

### CP-BP-12 — Succession handoff separated from authority/legitimacy

The source already has substantial succession architecture. Portable testing sharpened the operational distinction between successor designation, authority/permission and successful knowledge/capability handoff.

> **Succession ≠ Automatic Legitimacy**

> **Authority to Succeed ≠ Successful Handoff**

**Classification:** C / I / F
**Decision:** INCORPORATE as operational clarification without replacing constitutional succession.

### CP-BP-13 — Residual uncertainty and honest continuity claims

Continuity claims must not exceed recovery evidence; unresolved dependencies remain unresolved rather than being assumed satisfied or irrelevant.

**Classification:** C / G / F
**Decision:** INCORPORATE.

### CP-BP-14 — Recursive review of continuity mechanisms

Continuity mechanisms themselves can fossilise. The portable module makes review triggers and replacement capability explicit.

> **Continuity Mechanism ≠ Permanent Correctness**

**Classification:** C / G
**Decision:** INCORPORATE.

## 3. Recovered/source-family architecture

The Legacy Ladder already strongly supports the principle that preserving information alone is insufficient; practical knowledge, tools, infrastructure and prerequisite capability may be needed for recoverability.

Therefore that concept is classified partly as:

**R — Recovered architecture / source-family consolidation**

rather than being attributed to portable invention.

KCS remains the owner of detailed knowledge-state/dependency/change-propagation architecture. The Continuity companion should consume those functions where available, not absorb KCS.

## 4. Disposition

**BPM disposition: D2 — BOUNDED COMPANION UPGRADE**, with an R-class source-family consolidation component.

The Continuity Protocol V2 kernel remains intact.

No rewrite of the large constitutional source is justified.

Create:

**Continuity Protocol Companion Upgrade 001 — Operational Recovery and Verification Architecture**

## 5. Authority boundary

The companion must not:

- invent legitimate continuity objectives;
- set RTO/RPO/MAF values without the legitimate domain owner;
- create succession authority;
- resolve personal identity;
- make a preserved historical state current;
- certify recoverability without evidence;
- treat a named dependency as available;
- expand KCS ownership into Continuity;
- treat one disruption test as universal resilience.
